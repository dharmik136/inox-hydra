## Notes on the items

**Health lists the readers Setup listed.** The first draft of the table listed all nine readers, with the two network-reading parts marked "NOT SEEN YET, NETWORK READING". That brought back the defect cycle 2 removed as SETUP-17: network reading is off unless switched on, so the two rows read NOT SEEN YET for everyone, and the advice for that, open the matching page, cannot start them. `tests/test_qc_f4b_identity.py` caught it. The list now follows the same rule as the onboarding state, and `test_health_and_the_onboarding_state_list_the_same_readers` holds the two lists equal.

**The first view carries counts, not rows.** Returning every day row with the first view would have been nine readers by 180 days, past the 150 KB first-paint bar within six months of use. The runs and the day rows are one level down, read when a reader is opened (`test_the_first_view_carries_counts_and_not_rows`).

**Replies and Today agree.** Today's five and Replies' list come from the same rules: own posts, the 14-day window on when the studio first saw a comment, comments only, and Today's answered statuses. The creator's mark is one SQL statement, `replies.MARKED_AT`, read by both. Today's count is the number Replies lists; Today still names five people, ordered as before.

**Two controls called Answered.** The first draft named the view toggle and every row's button "Answered", and the browser test clicked the toggle instead of a comment's mark, which is what a screen reader user would have met too. Each row's button is now named for its comment ("Answered, Anika Shah's comment") and the toggle reads Marked answered.

**Audience is kept, not recomputed.** On the synthetic three year install, summing half a million interactions on each visit took about 700 ms, against the 100 ms bar, and a covering index did not help (the planner groups by lead either way). The per-person engagement is kept in memory per database and brought current from the rows added since; interaction rows are otherwise only inserted or deleted (their conflict path updates when a row was last seen and how often, which is not read), so a removal is detected by the row count and rebuilds, and a post becoming the creator's is adopted. Three tests hold the kept answer to a rebuild's in each of those cases.

**Gone quiet is relative to what was read.** The migration table points Audience's "gone quiet" at the silent-lead review query (`retention._SILENT_LEADS`). That query answers a different question, which people may be removed after 24 months untouched and never acted on: on most installs it is empty for two years, and on an old one it lists one-time reactors from years ago rather than regulars who stopped. Audience instead lists repeat engagers not seen since the last five posts whose engagers were read began, and abstains until five have been read. The review keeps its own rule in Storage and privacy. This is a divergence from the report's pointer, flagged for the reviewer.

**"Until Setup is done" is Setup's own rule.** Decision 5 and the brief say the studio opens on Setup until setup is done. Setup already says "Setup is done" only when all five of its steps are (the bridge heard from, the profile confirmed and read, the archive step, your posts read to the end), and the landing used a different line, the identity step alone. Both now read `lib/setup.ts`. The consequence, flagged for review: a creator who has confirmed their profile but not done the archive step lands on Setup each time, until they import the archive or say their account has no posts. Cycle 2's landing test (`tests/test_qc2_r5_first_load.py`) held the old line; it now seeds a finished Setup and keeps its "asks once" and "never draws the Composer" assertions, and `tests/test_qc4_t4_rail.py` holds both sides of the new line.

**Brand and Settings both open Brand Studio for now.** The split is phase b. Until then each entry opens the same screen, and its unsaved edits are registered under the entry showing it, so leaving Brand or Settings with edits asks first, as leaving Brand Studio did. The help sends grounding, security, storage and licence instructions to Settings and identity and watermark to Brand, where phase b will put them.

**Today's one thing to open.** When a reader drifts, Today's reason said "See Capture health in Setup.", beside a Go to Setup button. Setup no longer holds the block, so the sentence now reads "Health shows since when; Setup links to it." (`studio/backend/today.py:308`), which is true with the button as drawn. A `health` action with its own button would be the better fix, and needs `TodaySurface.tsx`, which is track 3's; it is listed below as a follow-up.
