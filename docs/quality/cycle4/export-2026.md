# 2.10.1, track 6: the real analytics export, and the phone against the real Telegram

The record of what this track changed for 2.10.1, after the owner's install met two real services on 2026-10-28: LinkedIn's analytics export, and Telegram. Branch `qc4/export-2026`, from `main` at 9e2adf7 (version 2.10.0, schema 35). No independent review this round: each item has a failing test first, and one full suite ran at the end. ## What the real services showed

- **The analytics export** (from the preview the owner's install showed; the owner's file was not read): a file named `AggregateAnalytics_<Creator Name>_2025-09-24_2026-10-28.xlsx`, with the sheets DISCOVERY (3 rows, totals over the range), ENGAGEMENT (400 rows, daily), MOST RECENT POSTS (3 rows), TOP POSTS, FOLLOWERS (400 rows, daily new followers and the total), AUDIENCE DEMOGRAPHICS and CONTENT DEMOGRAPHICS, each of the last two with the first row "Top Demographics, Value, Percentage". It imported 399 days of exact daily figures. MOST RECENT POSTS was refused as "a post's own export with 3 rows"; the two demographics sheets were not recognised.
- **Telegram**: the real service was exercised on 2026-10-28. Polling worked, and the bot received the owner's two messages; both were refused by chat id, because the panel had been saved with chat id "2" while the owner's chat is a nine-digit number, and the log said only "Unauthorized ingress attempt from chat_id: N". Once the chat id was fixed, a message was accepted and processed; the LinkedIn app's Copy link then gave a short link (`lnkd.in/p/<code>`), which became a draft by the text rule, with no desk request.
