# Risk - LinkedIn terms and detection

LinkedIn's User Agreement prohibits automated access and scraping. The product reads pages the creator opens rather than crawling, and gates every request to LinkedIn. It never comments, reacts, connects or messages. It does three things that are not reading, each only when the creator asks: it schedules a post through LinkedIn's private API (**Send to LinkedIn**, the paragraph below), it clicks and scrolls through the creator's own activity during a history import, and it clicks Start a post and types a draft into LinkedIn's composer without posting it.

**Tolerated in practice, not permitted in text (corrected cycle 4).** By LinkedIn's own words there is no carve-out for a passive, own-data, read-only extension: User Agreement 8.2 item 2 names "browser plugins and add-ons" used "to scrape or copy the Services, including profiles and other data" (https://www.linkedin.com/legal/user-agreement, effective 3 November 2025, read 26 October 2026), and the Help Center's triad is software that "scrape[s], modif[ies] the appearance of, or automate[s] activity" (https://www.linkedin.com/help/linkedin/answer/a1341387). The default mode touches items 2 and 15 lightly (reading your own pages; one invisible attribute on feed cards, and a banner during an import) and is tolerated in practice, not permitted in text; the lawyer's read in mitigation 5 should start from that distinction rather than from calling the default mode a defensible personal tool, as this note used to. The enforcement record draws the line the text does not: every documented action is about third-party data at scale, fake accounts, cookie reuse on vendor servers or UI overlay at scale, and none has reached a tool that reads only the member's own pages in the foreground. The creator-facing page in the help, `docs/help/where-each-feature-stands-with-linkedins-terms.md`, quotes the text verbatim and dated beside each feature's standing. A commercial product is judged more strictly.

**The enforcement record, dated (added cycle 4).** Shield wound down in May 2026: its team told its users "Both Google and LinkedIn have made it clear that we cannot continue operating Shield as it was built", as AuthoredUp quotes the notice (https://authoredup.com/blog/shield-analytics-winding-down, published 2026-05-15; Shield's own site returned HTTP 402 on 2026-10-26); the extension was pulled from the Chrome Web Store, and its method was the member's login cookie reused on Shield's servers for background sync [reported, a competitor quoting the notice]. Kleo's co-founder Jake Ward wrote on LinkedIn "After 2 years and 70,000+ users, the Kleo Chrome extension has to shut down. LinkedIn told us to." (https://www.linkedin.com/posts/jakezward_i-didnt-want-to-post-this-but-i-have-to-activity-7341796212687175681-JjZx, readable without signing in on 2026-10-26; the post shows no date, and its activity id gives 2025-06-20). The user count is his; other accounts give other counts and dates, and none was checked here. The extension overlaid LinkedIn's pages and read them, and Kleo relaunched as a paid web app. Taplio's founder wrote on X in November 2024 that LinkedIn "permanently suspended my account because of my Taplio involvement" (https://x.com/tibo_maker/status/1857104780558037021, as quoted at https://magicpost.in/blog/is-taplio-safe) [reported]. AuthoredUp, the closest analogue to this product's default mode (reads only pages the user opens, no background activity, no `cookies` permission, archive upload for history), has no reported incident. The ladder this gives: the default install reads foreground own pages with light in-page elements; the import and the composer click are actions on a press; network reading was a disclosed opt-in until its retirement in 2.10.2; Send to LinkedIn is the one feature squarely on 8.2 item 13, off by default and first profile only.

**Most exposed:** the scrolled [[History Import]], `linkedin_client.schedule_norm_share` ("Send to LinkedIn"), and the Agency tier's sessions: 8.2 item 1 bars using "another's account (such as sharing log-in credentials or copying cookies)" (https://www.linkedin.com/legal/user-agreement), five profiles on one machine is five accounts, and the tool cannot tell whose browser a session came from. The [[Voyager Interceptor]], which wrapped fetch inside LinkedIn's page, was retired with network reading in 2.10.2 and is no longer an exposure.

**Send to LinkedIn, named explicitly (added cycle 3).** `schedule_norm_share` (`linkedin_client.py:954-1030`) POSTs `{"lifecycleState": "SCHEDULED", "commentary": ..., "scheduledAt": ...}` to `https://www.linkedin.com/voyager/api/contentcreation/normShares`, an undocumented private endpoint, authenticated with the member's own `li_at` cookie and `JSESSIONID` as a CSRF token. That is a write, not a read: automated content creation on a personal profile through a private API, outside LinkedIn's published terms, and it could affect the account's standing if LinkedIn's systems treat it as automation. It is off by default (`INOX_ALLOW_LINKEDIN_EGRESS`, `egress.py:84`) and the owner has tested it personally, but it ships, so this register names it rather than relying on the Voyager interceptor and the history import to stand in for every exposure.

**Mitigations, in order:**
1. Done: Setup leads with [[LinkedIn Data Archive Import]], LinkedIn's own sanctioned export.
2. Done: "undetectable", "anti-detection" and "stealth" language is gone from the README, the extension doc and the interceptor ([[Gap - Claims the code contradicts]]).
3. Done: the interceptor is an explicit, off-by-default setting with its own disclosure. Retire it if the archive and page readers cover the need. Done (2.10.2): retired. LinkedIn's 2026 web app makes no `/voyager/api/` requests, so it read nothing; it, its switch and the `webRequest` permission are gone (`tests/test_network_reading_retired.py`).
4. Done (cycle 3): Send to LinkedIn requires a one-time, logged acknowledgement of the paragraph above before an installation's first send, separate from the per-send confirmation that names the account and the time. `docs/ARCHITECTURE.md` §4 and `docs/EXTENSION_AND_SYNC.md` §2 no longer claim zero automated activity or an unconditional "never click".
5. Get a lawyer's read on the extension before the public store listing. Brief it with the clause table in the help page above and with this note's wording: tolerated in practice, not permitted in text.
6. Done (cycle 4, D9): session sync and Send to LinkedIn work in the first creator profile only; the help says each profile's session must come from that creator's own browser on that creator's own machine.
7. Done (cycle 4, item 28): LinkedIn's own analytics export (.xlsx) is imported as the sanctioned source of exact figures, so the interceptor's retirement condition can be stated honestly: retire it once the analytics export import or an official analytics API covers exact figures, not once the archive covers it, since the archive carries no figures. Met: the interceptor was retired in 2.10.2.
8. Done (cycle 4, item 30): the creator-facing terms page in the help, and the store listing's Limited Use disclosures drafted in `release/STORE_DISCLOSURES.md`.
9. Open: the official posting route (Sign In with LinkedIn plus Share on LinkedIn) is parked on the public-client question, answered in `docs/OFFICIAL_POSTING_ROUTE.md`; the Community Management application is an owner action.
10. Keep a dated watch on three external texts that can move under the product: the two Help Center articles (one was updated within a month of 2026-10-26), the Member Post Analytics eligibility page, and the Chrome Web Store policies.
